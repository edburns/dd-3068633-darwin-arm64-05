### What worked well

- **Serial orchestration was correct.** The second task was based on the first task's merge commit, preserving implementation order.
- **Task boundaries were small and reviewable.** Each PR changed two files and received a clean first-round CCRA review.
- **HEAD-specific gates prevented stale validation.** Both stage-30 and stage-40 sessions rechecked the exact commit before transition and merge.
- **Repository-owned validation remained authoritative.** The campaign used the committed runner and pinned workflow rather than bypassing them.
- **The control condition was preserved.** Lesson propagation remained `off` in the manifest and every task invocation.

### Recommendations

1. **Persist unredacted aggregate token counters.** Add non-content input/output token totals to the run manifest or a separate metrics artifact so control and treatment campaigns can compare token efficiency without exposing prompts.
2. **Persist normalized per-task outcomes.** Record phase start/end, PR number, review rounds, comment totals, changed-file count, merge commit, and final status in structured JSON. The current report must combine Markdown transcripts with JSONL timestamps.
3. **Record orchestration overhead explicitly.** A campaign-level breakdown of session startup, inter-phase gaps, and finalization would explain the 7m 40s not represented by phase durations.
4. **Retain the existing review gates.** Current-HEAD review verification, unresolved-thread checks, base verification, and real-failure filtering produced a reproducible clean merge path.
5. **Use this run as the control baseline.** Its measured values—34m 22s wall clock, 177.40860 AIU, two clean first-round reviews, and zero comments—are suitable comparison points for an otherwise equivalent `LESSON_PROPAGATION=campaign` run.

No parent-directory `*memory*.md`, `*prompts.md`, or `*job-logs.txt` context artifacts were present; conclusions above are limited to the run manifest and phase artifacts in the shepherd log directory.
